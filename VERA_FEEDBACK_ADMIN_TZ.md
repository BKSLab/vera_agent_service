# ТЗ: постоянное хранение диалогов, обратная связь и админ-панель Веры

> **Статус:** проект требований для последующего уточнения и декомпозиции.
> **Дата:** 2026-07-29.
> **Сервис-владелец:** `vera_agent_service`.

---

## 1. Контекст

Agent Service уже реализован как FastAPI-приложение и является оркестратором диалога с Верой:

- получает пользовательские запросы через RabbitMQ;
- использует `session_id` как идентификатор истории диалога LangGraph;
- использует `request_id` как идентификатор отдельного запроса и канала SSE;
- восстанавливает оперативную историю из Redis checkpointer;
- формирует и стримит окончательный ответ;
- знает использованные инструменты, источники и результат обработки.

Сейчас Redis является оперативным хранилищем истории с TTL, а Phoenix и структурированные логи используются для наблюдаемости. Постоянного доменного хранилища диалогов и обратной связи в Agent Service нет.

На сайте уже реализована развёрнутая анкета обратной связи о Вере с отправкой по email. Дополнительно требуется оценка каждого ответа Веры кнопками «палец вверх» и «палец вниз».

Идентификаторы без сохранённого содержимого недостаточны для последующего анализа: администратор должен иметь возможность открыть конкретный ответ и весь связанный с ним диалог спустя длительное время, независимо от TTL Redis.

---

## 2. Цели

1. Сделать Agent Service единственным владельцем постоянной истории диалогов Веры.
2. Сохранять каждый пользовательский запрос и окончательный ответ агента в PostgreSQL.
3. Поддержать два независимых вида обратной связи:
   - быстрая оценка конкретного ответа — 👍/👎;
   - развёрнутая анкета по сессии.
4. Сохранять оба вида обратной связи в PostgreSQL.
5. Продолжить отправлять развёрнутые отзывы по email, но считать базу данных источником истины.
6. Реализовать защищённую административную панель непосредственно в Agent Service.
7. Дать администратору возможность перейти от отзыва к конкретному ответу и полной хронологии сессии.
8. Создать основу для дальнейшего контроля качества и экспертной проверки ответов Веры.

## 3. Границы ответственности

### 3.1. Agent Service отвечает за

- постоянное хранение сессий и отдельных реплик;
- связь `session_id` → сессия и `request_id` → конкретная реплика;
- сохранение точного пользовательского вопроса;
- сохранение фактически отправленного пользователю ответа;
- сохранение источников и основных технических метаданных ответа;
- приём, валидацию и сохранение обоих видов обратной связи;
- отправку или постановку в очередь email-уведомления о развёрнутом отзыве;
- хранение статуса email-доставки;
- административную панель и аналитические представления;
- политику хранения и удаления данных;
- аудит административного доступа к чувствительным данным.

### 3.2. Сайт отвечает за

- отображение чата;
- отображение 👍/👎 у каждого завершённого сообщения Веры;
- отображение развёрнутой анкеты;
- передачу `session_id`, `request_id` и пользовательской оценки в API Agent Service;
- локальное состояние выбранной оценки и понятную обратную связь пользователю;
- защитный proxy/BFF-слой, если он остаётся частью принятой схемы интеграции;
- CSRF-защиту и первичный rate limit на публичной стороне.

Сайт не должен передавать в качестве источника истины текст вопроса или ответа: Agent Service уже знает фактически обработанный вопрос и сформированный ответ. Данные из браузера нельзя использовать для восстановления или изменения сохранённого диалога.

### 3.3. Не меняется

- Redis checkpointer остаётся оперативной памятью LangGraph;
- RabbitMQ остаётся транспортом входящих задач;
- SSE остаётся транспортом потоковой доставки ответа;
- Phoenix остаётся системой наблюдаемости и трассировки;
- PostgreSQL не заменяет Redis или Phoenix, а становится постоянным доменным хранилищем для диалогов и обратной связи.

## 4. Термины и идентификаторы

- **Сессия** — последовательность сообщений одного диалога, идентифицируется `session_id`.
- **Реплика / ход диалога** — один пользовательский запрос и связанный с ним ответ Веры, идентифицируется `request_id`.
- **Оценка ответа** — 👍 или 👎 для одной реплики.
- **Отзыв по сессии** — развёрнутая анкета о консультации в целом.
- **Источник** — документ, статья или норма, использованные при формировании ответа.

Требования к идентификаторам:

- `session_id` обязателен для любого вида обратной связи;
- `request_id` обязателен для оценки конкретного ответа;
- `request_id` уникален в постоянном хранилище;
- Agent Service проверяет, что переданный `request_id` относится к переданному `session_id`;
- технические повторы RabbitMQ не должны создавать дубли реплик.

## 5. Функциональные требования

### 5.1. Постоянное хранение сессий

Agent Service должен:

- создавать сессию при первом успешно принятом запросе с новым `session_id`;
- связывать сессию с `user_id`, если пользователь авторизован;
- поддерживать дату создания и дату последней активности;
- позволять получить все реплики сессии в хронологическом порядке;
- не создавать новую сессию при повторной доставке того же запроса;
- не считать Redis единственным источником данных для административного просмотра.

### 5.2. Постоянное хранение реплик

Для каждого `request_id` необходимо сохранять:

- `session_id`;
- `request_id`;
- `user_id`, если он известен;
- точный текст пользовательского запроса;
- окончательный текст, отправленный пользователю;
- использованные источники в структурированном виде;
- использованные инструменты или маршрут обработки в объёме, необходимом для анализа;
- статус обработки;
- время начала и завершения;
- длительность обработки;
- сведения об ошибке без секретов и чувствительных технических подробностей.

Минимальные статусы реплики:

- `processing`;
- `completed`;
- `failed`;
- `delivery_unconfirmed`, если ответ сформирован, но его доставка клиенту не подтверждена.

Требования к сохранению:

- сохраняется именно фактически сформированный финальный ответ, а не промежуточный анализ LLM;
- запись по `request_id` должна быть идемпотентной;
- повтор RabbitMQ-сообщения не должен повторно генерировать или дублировать уже завершённую запись;
- ошибка постоянного хранилища после начала стриминга не должна запускать повторную генерацию и создавать дубли ответа;
- временная ошибка сохранения должна регистрироваться и обрабатываться отдельным механизмом повторной записи;
- отсутствие PostgreSQL не должно приводить к склеиванию, повтору или потере уже начатого пользовательского ответа.

### 5.3. Оценка конкретного ответа — 👍/👎

Для каждого завершённого ответа Веры сайт отображает две взаимоисключающие кнопки:

- положительная оценка;
- отрицательная оценка.

Agent Service должен:

- принимать `session_id`, `request_id` и значение оценки;
- проверять существование реплики и принадлежность сессии;
- запрещать оценку незавершённой или несуществующей реплики;
- поддерживать повторное нажатие без создания дубля;
- поддерживать изменение 👍 на 👎 и обратно;
- поддерживать отмену оценки, если это будет предусмотрено интерфейсом;
- хранить дату создания и последнего изменения оценки;
- возвращать текущее состояние оценки;
- применять rate limit и защиту от автоматического спама.

Для одной реплики в рамках одной пользовательской сессии должна существовать не более чем одна активная оценка.

### 5.4. Развёрнутый отзыв по сессии

Сохраняются существующие поля анкеты:

- `session_id` — обязательно;
- аудитория пользователя:
  - соискатель или работник с инвалидностью;
  - работодатель или представитель работодателя;
  - другое;
- полезность консультации — целое число от 1 до 5;
- доверие к ответу — целое число от 1 до 5;
- свободный комментарий;
- контактный email.

Все ответы анкеты, кроме `session_id`, остаются необязательными в соответствии с текущим интерфейсом.

Дополнительные требования:

- отзыв связывается с существующей сессией;
- интерфейс сайта должен предлагать отзыв после появления хотя бы одного завершённого ответа;
- одна сессия может иметь несколько отправок анкеты, каждая хранится отдельной записью;
- повтор транспортного запроса с тем же ключом идемпотентности не создаёт дубль;
- комментарий и email проходят серверную валидацию;
- email и комментарий не записываются в обычные application-логи или telemetry spans.

### 5.5. Email-уведомление

Для каждого развёрнутого отзыва:

1. Сначала создаётся запись в PostgreSQL.
2. После успешного сохранения инициируется отправка email.
3. Результат доставки фиксируется в записи отзыва.

Минимальные статусы email:

- `pending`;
- `sent`;
- `failed`;
- `not_requested`, если уведомление отключено конфигурацией.

Необходимо хранить:

- дату успешной отправки;
- количество попыток;
- дату последней попытки;
- безопасное описание последней ошибки без SMTP-секретов.

Ошибка email не должна отменять сохранённый отзыв и не должна приводить к повторному созданию отзыва. Должна поддерживаться безопасная повторная отправка из фонового процесса или админки.

### 5.6. Административная панель

Административная панель реализуется внутри FastAPI-приложения Agent Service. Допускается использование SQLAdmin после утверждения паттернов реализации.

Панель должна быть недоступна без отдельной административной аутентификации.

#### 5.6.1. Главная страница

Минимальная сводка:

- количество сессий и реплик за период;
- количество 👍 и 👎;
- доля отрицательных оценок;
- средняя полезность;
- среднее доверие;
- количество развёрнутых отзывов;
- количество неотправленных email;
- количество ошибочных или незавершённых реплик.

#### 5.6.2. Оценки ответов

Список должен показывать:

- 👍 или 👎;
- дату оценки;
- дату ответа;
- краткий текст вопроса;
- краткий фрагмент ответа;
- `session_id`;
- `request_id`;
- статус экспертной проверки.

Фильтры:

- тип оценки;
- период;
- статус реплики;
- статус экспертной проверки;
- наличие или отсутствие источников;
- поиск по `session_id` и `request_id`;
- поиск по тексту вопроса и ответа, если выбранное хранилище и требования безопасности это допускают.

#### 5.6.3. Карточка реплики

Карточка должна показывать:

- полный вопрос пользователя;
- полный фактически отправленный ответ;
- список источников;
- оценку пользователя;
- дату и длительность обработки;
- статус;
- основные инструменты или маршрут обработки;
- технические идентификаторы с возможностью копирования;
- ссылку «Открыть всю сессию».

Реплика, по которой открыта карточка, должна быть визуально выделена в контексте сессии.

#### 5.6.4. Развёрнутые отзывы

Список должен показывать:

- дату;
- аудиторию;
- полезность;
- доверие;
- наличие комментария;
- маскированный контактный email;
- статус отправки email;
- `session_id`;
- статус экспертной обработки.

Из записи отзыва администратор должен переходить к полной сессии.

#### 5.6.5. Карточка сессии

Карточка сессии должна показывать:

- хронологию всех сохранённых реплик;
- вопросы и ответы в виде диалога;
- оценки рядом с соответствующими ответами;
- развёрнутые отзывы по сессии;
- источники ответов;
- даты и длительность обработки;
- пользователя, если он был авторизован;
- технические идентификаторы;
- ошибки и деградации без вывода секретов;
- отметки экспертной проверки.

При переходе из оценки конкретного ответа соответствующая реплика должна быть подсвечена и автоматически находиться в видимой области.

#### 5.6.6. Экспертная обработка

Минимальные статусы:

- `new`;
- `in_review`;
- `resolved`;
- `dismissed`.

Администратор или эксперт должен иметь возможность:

- назначить статус;
- оставить внутреннюю заметку;
- добавить теги причины, например:
  - неверный ответ;
  - недостаточно источников;
  - непонятная формулировка;
  - устаревшая норма;
  - техническая ошибка;
  - нерелевантный вопрос;
- сохранить автора и дату изменения.

Внутренние заметки не должны быть видны пользователю и не должны изменять сохранённый текст исходного ответа.

#### 5.6.7. Экспорт

Необходимо предусмотреть экспорт отфильтрованных данных в CSV или JSON без раскрытия лишних персональных данных. Экспорт нужен для:

- анализа отрицательных оценок;
- формирования набора проверочных вопросов;
- экспертной разметки;
- последующей оценки качества агента.

Экспорт полного контактного email допускается только для явно авторизованной административной роли.

## 6. Предлагаемая модель данных

Имена окончательно утверждаются при выборе паттернов, но логически нужны четыре сущности.

### 6.1. `vera_chat_sessions`

Минимальные поля:

- внутренний UUID;
- уникальный `session_id`;
- `user_id`, nullable;
- `created_at`;
- `last_activity_at`;
- `closed_at`, nullable;
- служебные метаданные без чувствительного содержимого.

### 6.2. `vera_chat_turns`

Минимальные поля:

- внутренний UUID;
- внешний уникальный `request_id`;
- внешний `session_id` или FK на сессию;
- порядковый номер реплики в сессии;
- `user_id`, nullable;
- текст вопроса;
- текст ответа, nullable до завершения;
- структурированные источники, предпочтительно JSONB;
- структурированные технические метаданные, предпочтительно JSONB;
- статус;
- безопасное описание ошибки, nullable;
- `started_at`;
- `completed_at`, nullable;
- `latency_ms`, nullable;
- `created_at`;
- `updated_at`.

Индексы:

- уникальный индекс по `request_id`;
- индекс по `session_id`;
- составной индекс по `session_id` и времени/порядку;
- индекс по статусу и дате.

### 6.3. `vera_message_feedback`

Минимальные поля:

- внутренний UUID;
- FK на `vera_chat_turns`;
- значение `up` или `down`;
- статус экспертной проверки;
- внутренняя заметка эксперта, nullable;
- теги, nullable;
- `created_at`;
- `updated_at`;
- автор последнего административного изменения, nullable.

Ограничения:

- не более одной активной оценки для одной реплики в рамках текущей модели;
- связь с сессией определяется через реплику;
- изменение оценки обновляет существующую запись, а не создаёт новую активную запись.

### 6.4. `vera_session_feedback`

Минимальные поля:

- внутренний UUID;
- FK на `vera_chat_sessions`;
- ключ идемпотентности отправки;
- аудитория, nullable;
- полезность 1–5, nullable;
- доверие 1–5, nullable;
- комментарий, nullable;
- контактный email, nullable;
- статус email;
- количество попыток email;
- дата последней попытки;
- дата успешной отправки;
- безопасное описание последней ошибки;
- статус экспертной проверки;
- внутренняя заметка эксперта;
- теги;
- `created_at`;
- `updated_at`.

## 7. API Agent Service

Точные пути и схемы утверждаются после добавления проектных FastAPI-паттернов.

### 7.1. Публичный контур через proxy сайта

Минимально необходимы операции:

- создать или изменить 👍/👎 для `request_id`;
- получить текущее состояние оценки ответа;
- отменить оценку, если это поддерживает интерфейс;
- создать развёрнутый отзыв по `session_id`.

Пример логического контракта оценки:

```json
{
  "session_id": "conversation-uuid",
  "request_id": "message-uuid",
  "value": "down"
}
```

Пример логического контракта анкеты:

```json
{
  "session_id": "conversation-uuid",
  "submission_id": "feedback-submission-uuid",
  "audience": "employer",
  "usefulness": 3,
  "trust": 2,
  "comment": "Не хватило пояснения по источнику",
  "contact_email": "user@example.ru"
}
```

### 7.2. Требования к API

- строгая Pydantic-валидация;
- ограничение длины строк;
- идемпотентность мутирующих операций;
- единый формат ошибок;
- request ID для трассировки HTTP-запроса;
- rate limit;
- проверка связи `session_id` и `request_id`;
- запрет принимать текст вопроса и ответа как доверенные данные от сайта;
- отсутствие персональных данных в логах;
- обратная совместимость при поэтапном переключении сайта;
- документированный OpenAPI-контракт.

### 7.3. Доступ сайта к Agent Service

Предпочтительный поток:

```text
Браузер → proxy/BFF сайта → защищённый API Agent Service → PostgreSQL
```

Agent Service не должен доверять произвольному публичному вызову только потому, что в нём переданы корректно выглядящие UUID. Необходимо предусмотреть сервисную аутентификацию proxy сайта и отдельную защиту административного контура.

## 8. Безопасность и персональные данные

- административная панель закрыта отдельной аутентификацией;
- административные и публичные маршруты разделены;
- служебный API между сайтом и Agent Service аутентифицируется;
- секреты не передаются в браузер;
- contact email маскируется в списках;
- полный email доступен только в карточке при наличии необходимых прав;
- комментарии и email не записываются в application-логи, Phoenix spans и тексты ошибок;
- HTML и пользовательский текст безопасно экранируются при отображении и формировании email;
- административные действия с экспертным статусом и заметками аудируются;
- экспорт чувствительных данных ограничен;
- сроки хранения диалогов и отзывов задаются конфигурацией и документируются;
- должна быть предусмотрена процедура удаления или обезличивания данных пользователя;
- IP-адрес не сохраняется без отдельного обоснования;
- публичные endpoints защищены rate limit на стороне сайта и Agent Service;
- SQLAdmin или другая админка не публикуется наружу без TLS и сетевых ограничений.

---

## 9. Надёжность и согласованность

- сохранение реплики идемпотентно по `request_id`;
- повторная доставка RabbitMQ не создаёт дубли;
- сохранение отзыва предшествует отправке email;
- email-ошибка не удаляет отзыв;
- повтор email не создаёт новый отзыв;
- повтор API-запроса с тем же ключом идемпотентности возвращает исходный результат;
- конкурентные оценки одного ответа не создают несколько активных записей;
- ошибка аналитического хранилища не приводит к повторной отправке уже начатого ответа пользователю;
- миграции БД выполняются до запуска версии приложения, использующей новую схему;
- health/readiness должны различать критичность PostgreSQL для административных и пользовательских сценариев;
- должен существовать контролируемый режим деградации, если PostgreSQL временно недоступен.

## 10. Наблюдаемость

Необходимо добавить метрики и структурированные события:

- успешные и ошибочные сохранения сессий и реплик;
- количество 👍 и 👎;
- количество созданных анкет;
- ошибки валидации и rate limit;
- pending/failed email;
- длительность операций БД;
- ошибки административных запросов;
- количество реплик, потерявших связь с сессией;
- попытки оценки неизвестного `request_id`;
- очередь или количество операций, ожидающих повторной записи.

В логах допустимы `session_id`, `request_id` и внутренние UUID при утверждённой политике, но не полный текст вопроса, ответа, комментария или email.

## 12. Тестирование

### 12.1. Unit

- валидация всех входных схем;
- связь `session_id` и `request_id`;
- создание и обновление оценки;
- отмена оценки;
- идемпотентность;
- ограничения рейтингов 1–5;
- переходы email-статусов;
- переходы экспертных статусов;
- маскирование email;
- безопасное форматирование пользовательского текста.

### 12.2. Integration

- реальные миграции PostgreSQL;
- сохранение завершённой реплики;
- сохранение failed-реплики;
- повтор RabbitMQ-сообщения;
- конкурентные оценки;
- сохранение анкеты и постановка email на отправку;
- повтор email после ошибки;
- фильтры административной панели;
- открытие сессии и хронологии;
- подсветка реплики из конкретного отзыва;
- административная авторизация;
- запрет доступа без авторизации.

### 12.3. Сквозные сценарии

1. Пользователь получает ответ, ставит 👎, администратор открывает оценку, видит вопрос, полный ответ, источники и всю сессию.
2. Пользователь меняет 👎 на 👍, в БД остаётся одна активная оценка.
3. Пользователь отправляет развёрнутую анкету, запись появляется в админке до отправки email.
4. SMTP временно недоступен: отзыв сохранён, статус `failed`, повторная отправка не создаёт дубль.
5. Повтор RabbitMQ-запроса не создаёт вторую реплику.
6. PostgreSQL недоступен после начала SSE: ответ не генерируется повторно и не дублируется.
7. Неавторизованный пользователь не получает доступ к админке.
8. Администратор фильтрует 👎 без источников и экспортирует обезличенный набор.

## 13. Критерии приёмки

- каждый успешно сформированный ответ имеет одну постоянную запись с уникальным `request_id`;
- все реплики одной сессии открываются в хронологическом порядке;
- оценка ответа однозначно связана с сохранённой репликой;
- администратор из оценки переходит к полному ответу и всей сессии;
- развёрнутый отзыв сохраняется в БД и отображается в админке;
- email отправляется после сохранения и имеет наблюдаемый статус;
- повторные запросы не создают дубли;
- сайт не передаёт текст ответа как доверенный источник;
- Redis TTL не влияет на просмотр уже сохранённых диалогов;
- административная панель недоступна без авторизации;
- персональные данные не попадают в логи и telemetry;
- основные сценарии покрыты unit, integration и сквозными тестами;
- существующий чат и SSE-корреляция по `request_id` продолжают работать без регрессий.

1. Утвердить паттерны FastAPI, БД, миграций, фоновых задач и админки.

7. Реализовать административную панель.
8. Интегрировать сайт с новым API.

10. Выполнить поэтапное включение и наблюдение метрик.

Каждый этап перед началом разработки необходимо декомпозировать на проверяемые подзадачи с Definition of Done.

## 15. Вне рамок первой реализации

- автоматическая LLM-оценка всех ответов;
- автоматическое исправление или повторная генерация по 👎;
- редактирование исходного ответа администратором;
- управление корпусом RAG из этой админки;
- полноценная BI-система;
- замена Phoenix собственной системой трассировки;
- публичный кабинет пользователя с историей всех диалогов;
- объединение сессий одного пользователя между устройствами;
- обучение модели непосредственно из административной панели.

Эти направления могут использовать накопленные данные позднее, но не должны усложнять первый релиз.
